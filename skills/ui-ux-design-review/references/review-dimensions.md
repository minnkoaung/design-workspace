# Screen-specific review dimensions

Use only relevant dimensions, but assess them independently of DRD field coverage. Cite observed evidence and user impact. A dimension may remain unverified when its evidence is unavailable; that must constrain the conclusion.

| Dimension | Review questions | Evidence and limits |
| --- | --- | --- |
| Purpose and hierarchy | Can users identify the page's purpose, important information and next action? Do grouping and reading order support the task? | Actual screen layout and content; an inventory cannot establish visual hierarchy. |
| Navigation and orientation | Are entry, return, cancel and completion paths understandable? Are labels consistent with destinations? | Visible controls and agreed flow; test links only if a prototype/runtime is actually available. |
| Forms | Are persistent labels, field order, grouping, guidance, entered values and required/optional distinctions understandable? Are save/create/cancel consequences clear? | Inspect controls and field content; missing validation policy stays a product dependency. Default screens do not prove validation or submission behavior. |
| Tables and lists | Can people scan identifying fields, distinguish rows, understand statuses and associate actions with the correct record? Does column order/width suit the task? | Inspect actual rendered text and data density at the approved viewport. Search/filters/pagination are not automatically required. |
| Actions and consequences | Is the primary action clear? Are consequential actions distinguishable and tied to an identifiable target? Does confirmation explain the relevant consequence and destination? | Visible wording, target/context and hierarchy; do not invent a confirmation requirement for every action. |
| Authentication and permissions | Are sign-in/recovery/mandatory-change purposes and intended transitions clear? Are admin-only actions represented consistently with the DRD? | Design visibility and annotations can show intent; runtime RBAC, security and session enforcement remain unverified without executable evidence. |
| Feedback and recovery | Does the approved scope explain progress, outcomes, errors and recovery? Are required-but-deferred states accounted for? | Review built states if authorized; default states alone do not prove error handling. Do not build or demand deferred frames as current-scope defects. |
| Content and terminology | Are labels, instructions, statuses and consequence messages clear, consistent and source-supported? Is example data clearly distinct from product policy? | Compare DRD terminology and prescribed copy; distinguish exact-copy requirements from semantic equivalence. |
| Foundations and consistency | Do actual screens reuse approved patterns, typography, spacing, components and tokens consistently? | Inspect styles/bindings where available and rendered output. If the shared kit has a defect, flag it even when reused correctly; do not silently change the kit. |
| Accessibility | Are text, labels, contrast, status distinctions, control affordances and target sizes assessable and usable? Is meaning carried only by color where relevant? | Measure actual values for numeric claims. Static Figma does not establish keyboard/focus, DOM semantics, reading order in assistive technology or screen-reader operation. |
| Responsive/language scope | Does content fit the approved viewport/language, including long real labels/data? Is other requested coverage built or explicitly deferred? | Inspect approved frames only. Do not infer responsive behavior or translated layouts from one desktop screen. |
| Flow coherence | Do the represented screens agree on identity, permissions, data, actions and outcomes across the journey? | Cross-screen review plus prototype/runtime only when available. A missing requested connection differs from an unrequested prototype. |

For proposed improvements, explain the task problem first, then a proportionate change within the existing direction. Do not recommend common UI patterns simply because they are popular. If a recommendation changes product behavior, label it a proposal and identify the necessary decision.
